# P8_PAD_PAGE — /pad/ virtual controller page

**Owns (only):** `platform/server/src/padPage.ts`
**Contract:** `padPage.ts` signature (frozen) · shared PadLayout/PADS · docs/PLATFORM.md §4.4.

## Mission
One server-generated HTML page (inline CSS+JS, no build step, like launcherHtml) that turns
any phone into a game controller for a specific game.

Flow: parse `?game=<id>&r=<roomId>` → fetch `/api/pads/<id>` for the PadLayout → render
sticks/buttons → prompt for the 6-char pairing code (big input, auto-uppercase,
CLAIM_ALPHABET keyboard hint) → open `ws(s)://host/ws` → send
`{t:'join_as_pad', room:<from r param>, token:<code>}`.

The PLAYER's `pad_pair` reply supplies urlPath already containing both game id and room id;
the pad never invents either.

After bind (`pad_joined`): stream `{t:'pad_input', seq++, lx,ly,rx,ry, buttons}` at ≤30Hz from
pointer state; show live RTT from `pad_input_echo.seq` matching; handle `pad_rejected` with a
readable error + re-enter-code state; on ws close show "disconnected".

Rendering rules: fullscreen dark paper (#14171c-family), touch-action none, landscape-friendly
flex layout; sticks = left/right pads per layout.sticks (id 'l'→left side, 'r'→right side);
buttons grid from layout.buttons (label text); bit 31 always rendered as ⏸ (reserved pause).
No external assets/fonts; system-ui stack.

## Rules
Pure function renderPadPage(opts) → full HTML string; never throws (bad layout → still return
a usable page with an error banner). Strict TS. No test file required; INT smoke-tests it.
